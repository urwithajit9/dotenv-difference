# dotenv-difference

Do all `.env` loaders read the same file the same way? No. This repo is a small test harness that feeds 16 `.env` fixtures to six readers and records what each one sees.

Companion to the article **[One .env file, three answers: measuring how dotenv readers disagree](https://dev.to/ajitkumar/one-env-file-three-answers-measuring-how-dotenv-readers-disagree-2oph)**.

## The result in one line

```text
API_KEY=   # fill this in later
```

| Reader | Value of `API_KEY` |
|---|---|
| Docker Compose, python-dotenv | `# fill this in later` |
| `docker run --env-file` | `␣␣␣# fill this in later` (leading spaces kept) |
| Node `dotenv`, bash `source` | `""` (empty) |

Across all 16 fixtures, **13 give different results depending on the reader**. Only bare keys, duplicate keys and an empty file are identical everywhere. The full table is in [`results/comparison.md`](results/comparison.md).

## What's measured

| Reader | Version | How it's run |
|---|---|---|
| python-dotenv | 1.2.2 | `readers/py_dotenv_all.py` |
| Node `dotenv` (with and without `dotenv-expand`) | 18.0.9 / 12.0.1 | `readers/node_dotenv_all.js` |
| bash `source` | GNU bash 5.3.9 | `readers/bash_source.sh` |
| Docker Compose `env_file:` | v5.3.1 | `readers/docker_env.sh compose` |
| `docker run --env-file` | Docker 29.6.2 | `readers/docker_env.sh run` |

Not measured yet: godotenv, dotenvy, Ruby dotenv (see [Add a reader](#add-a-reader)).

## Repository structure

```text
dotenv-difference/
├── cases/                  # 16 generated .env fixtures (one per edge case)
├── readers/                # one adapter per reader; each prints JSON
│   ├── py_dotenv.py        #   python-dotenv, single file
│   ├── py_dotenv_all.py    #   python-dotenv, whole directory
│   ├── node_dotenv_all.js  #   Node dotenv + dotenv-expand
│   ├── bash_source.sh      #   bash `source`
│   └── docker_env.sh       #   Docker Compose and `docker run --env-file`
├── results/                # JSON output from every reader + the comparison table
│   ├── python-dotenv.json
│   ├── node-dotenv.json
│   ├── bash-source.json
│   ├── compose.json
│   ├── docker-run.json
│   └── comparison.md       #   generated by compare.py
├── make_cases.py           # writes cases/*.env with exact bytes
├── compare.py              # results/*.json -> Markdown comparison table
├── fuzz.py                 # differential fuzzing: python-dotenv vs Node
├── run_all.sh              # regenerate everything
├── requirements.txt        # python-dotenv==1.2.2
├── package.json            # dotenv@18.0.9, dotenv-expand@12.0.1 (pinned)
└── .github/workflows/      # CI: fail if committed results are stale
```

| Folder or file | What it's for |
|---|---|
| `cases/` | The test inputs. Generated by `make_cases.py`, not edited by hand, because CRLF and BOM bytes are easy to mangle in an editor. |
| `readers/` | Adapters. Each takes a file or a directory and prints what its reader sees as JSON. |
| `results/` | Output of every adapter. Committed, so you can read the results without running anything, and so a dependency bump shows up as a diff. |
| `compare.py` | Reads the result files and builds the table. A reader whose results file is missing is skipped, so it works without Docker. |
| `fuzz.py` | Random one-line files through python-dotenv and Node to find differences nobody listed. |

## Quick start

You need Python 3, Node 22, bash 4.3+ (macOS ships 3.2, so install a newer one) and, for the Docker columns, Docker with Compose v2+.

```bash
git clone https://github.com/urwithajit9/dotenv-difference.git
cd dotenv-difference

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm ci

./run_all.sh                 # builds cases/, runs every reader, writes results/
cat results/comparison.md    # the table from the article
```

The first Docker run pulls `alpine:3.20`. The whole run takes about a minute, mostly starting one container per fixture and reader.

**No Docker?** Run the first three readers, and `compare.py` skips the Docker columns:

```bash
python3 make_cases.py
mkdir -p results
python3 readers/py_dotenv_all.py cases/ --out results/python-dotenv.json
node readers/node_dotenv_all.js cases/ --out results/node-dotenv.json
./readers/bash_source.sh cases/ > results/bash-source.json
python3 compare.py --cases cases/
```

## Run one reader on one fixture

```bash
python3 readers/py_dotenv_all.py cases/empty_comment.env
node    readers/node_dotenv_all.js cases/empty_comment.env
./readers/bash_source.sh           cases/empty_comment.env
./readers/docker_env.sh compose    cases/empty_comment.env
./readers/docker_env.sh run        cases/empty_comment.env
```

Pass a directory instead of a file to get every fixture in one JSON object.

## Fuzzing

```bash
python3 fuzz.py              # seed 0, 2000 random lines
python3 fuzz.py 0 20000      # seed 0, 20000 lines
python3 fuzz.py 7 5000       # your own seed and count
```

It prints how many random lines the two readers disagree on, the shortest examples, and which characters those lines contain. Using the same seed gives the same lines. It covers python-dotenv and Node only. Bash executes its input and the Docker parsers need a container per line, so neither is included.

Three ways to read along:

1. **Just look.** Open `results/comparison.md`. Nothing to install.
2. **Reproduce everything.** Follow [Quick start](#quick-start). Your `results/` should match the committed files. If a cell differs, check your tool versions first.
3. **Step by step.** Follow the article section by section and run each command from the table above. To get the code exactly as published, check out the tagged version: `git checkout blog-v1`.

## Reading the result files

Every adapter writes one JSON object keyed by fixture name. The shapes differ slightly:

| File | Shape per fixture |
|---|---|
| `python-dotenv.json` | `{"KEY": "value", ...}`, or `{"error": "..."}` |
| `node-dotenv.json` | `{"plain": {...}, "expanded": {...}}` (`expanded` applies `dotenv-expand`) |
| `bash-source.json`, `compose.json`, `docker-run.json` | `{"exit": 0, "values": {...}, "stderr": "..."}` (`stderr` only if non-empty) |

`compare.py` turns these into one table. A `⚠ error` in a cell means the reader exited non-zero. `␣` marks a run of spaces, `⏎` a line break in the fixture, and `\ufeff` the byte order mark.

## Add a reader

1. Write an adapter in `readers/` that takes a file or directory and prints JSON in the `{"exit", "values"}` shape.
2. Save its output as `results/<name>.json`.
3. Add one line to `COLUMNS` in `compare.py`: `"name": ("name.json", lambda e: e["values"], True)`.
4. Add the command to `run_all.sh` and open a pull request with the regenerated `results/`.

godotenv (`godotenv.Read`), dotenvy (`dotenvy::from_path_iter`) and Ruby dotenv (`Dotenv.parse`) are the obvious next ones.

## Safety

- **`readers/bash_source.sh` executes each file.** The fixtures are harmless. Never point it at a real `.env` or any file you don't trust, because `source` runs `$(...)` and backticks.
- The fixtures contain fake values only. Don't commit real secrets into `cases/`.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `ModuleNotFoundError: No module named 'dotenv'` | Activate the venv (`source .venv/bin/activate`) and run `pip install -r requirements.txt`. |
| `IndexError` from an adapter | It needs a path argument, for example `cases/empty_comment.env`. |
| `python-dotenv could not parse statement...` | Expected. It comes from the `unterminated` fixture and is the only signal python-dotenv gives. |
| `declare: -n: invalid option` | Your bash is older than 4.3 (common on macOS). Install a newer bash. |
| `env: unrecognized option: 0` in a Docker run | The image's `env` lacks `-0`. Use `IMAGE=debian:12-slim ./readers/docker_env.sh run cases/`, and use the same image for both modes. |
| `permission denied` from Docker | Add your user to the `docker` group, or run with `sudo`. |
| A result cell differs from the article | Compare tool versions with the table above. Loaders change behavior between releases, and that is what this repo detects. |

## CI

`.github/workflows/dotenv-matrix.yml` reruns `./run_all.sh` on every pull request and fails if the committed `results/` are stale. Because everything is pinned, a dependency bump that changes how a loader parses a line shows up as a diff in `results/`.
